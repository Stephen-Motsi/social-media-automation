A. PRODUCT IDENTITY

Application name/branding
- Name used by code when BRAND_NAME is not set: Social Automation.
- No separate logo asset or fixed product-name lockup was identified. Branding is mostly text in src/app/page.tsx and src/app/subscribe/page.tsx.

Main purpose
- A staff/admin dashboard for creating adverts, generating or uploading media,
  checking policy limits, connecting social accounts, scheduling content, and
  publishing adverts or posts across supported platforms.
- A public-facing subscription area lets people opt in by topic to receive
  matching WhatsApp adverts, while signed-in users can also subscribe to listed
  adverts and view received items.

Target users
- Ordinary users: sign in, manage advert subscriptions, connect their own
  WhatsApp/social handles, and review received deliveries.
- Staff admins: manage adverts, channels, audiences, approvals, posts and
  publishing.
- Super admins: additionally manage users and roles, sessions, notifications and
  audit logs.

Current implementation status
- Implemented in code: authentication, roles, database-backed sessions, advert
  creation and listing, subscriber matching/consent, approvals, channels,
  scheduling, policy review, notifications, activity logs, public subscription.
- Partially implemented or unverified: real delivery and live social account
  integration; repository documentation and mock/API client tests indicate these
  need live credentials and platform verification.
- See the README status and blockers before making any live delivery claim.

D. AUTOMATION AND BACKEND

Framework and architecture
- Next.js 15 App Router, React 19, TypeScript, Tailwind CSS 4.
- Server Components, Server Actions, API route handlers, middleware, Auth.js v5.
- PostgreSQL 16 plus Prisma 6.16.2.
- Redis 7 plus BullMQ 5.58.5 for publishing, campaign, handle delivery and delayed
  queue jobs.
- BullMQ workers run separately; Next.js itself does not perform scheduled sends.

Important API/routes
- Auth: GET/POST /api/auth/[...nextauth]
- Media public retrieval: GET /api/media/[id]
- Upload: POST /api/uploads
- Meta OAuth connect/callback: GET /api/meta/connect,
  GET /api/meta/callback
- X OAuth connect/callback: GET /api/x/connect, GET /api/x/callback
- TikTok OAuth connect/callback: GET /api/tiktok/connect,
  GET /api/tiktok/callback
- Meta webhooks: GET/POST /api/webhooks/meta

Background automation
- Three BullMQ queue types: publish-post, send-campaign, deliver-subscription.
- src/worker/index.ts runs workers, channel schedule checks, requeue safety,
  audience matching, delivery handling, and unconfirmed-subscription expiration.
- The default scheduler tick is 30 seconds via SCHEDULER_TICK_MS.
- requeueMissed queues due missed sends when Redis/worker availability resumes.
- No n8n configuration or integration is present in package dependencies or
  source code. Status: Not configured / not integrated.

Authentication/session
- Credentials plus Google/Facebook OAuth. Each sign-in creates a UserSession and
  ActivityLog row. Signed cookie stores a session ID rather than relying on
  mutable JWT role claims.
- Server and page actions validate active database session and current role.
  Sessions expire after 30 days, lastSeen is throttled, and users/staff can revoke
  sessions.
- Staff cannot sign in via social providers for an existing password account in
  order to avoid account takeover. Social accounts are linked by provider and
  provider account ID.

External services
- OpenAI for image generation and moderation.
- Meta, X, and TikTok APIs for account connection/publishing.
- PostgreSQL and Redis for state/jobs.
- Cloudflare tunnel/hosting instructions are documentation only; no deployment
  integration is verified here.

F. SECURITY, PRIVACY AND TRUST

Authentication/authorization
- Current database-backed sessions and server role checks are implemented.
- Super-admin-only operations are checked by requireSuperAdmin/server actions.
- Middleware is coarse and access decisions are repeated on the server.
- Passwords are bcrypt hashed. Social staff takeover by matching email is refused.
- Open redirect risk is reduced by safe callback path checks.

Social token handling
- Platform access/refresh tokens are encrypted with AES-256-GCM before storage,
  when stored through the SocialAccount token helpers.
- X/TikTok refresh paths exist and token refresh failures can block delivery until
  credentials reconnect; README describes token-health alerting as future work.
- Webhook Meta signatures use X-Hub-Signature-256 verification.

Data storage/deletion
- PostgreSQL stores application, consent, sessions, audits, subscriber, campaign,
  and media records; image bytes are stored in Postgres.
- Admins can delete an Audience Subscriber record, which cascades data depending
  on Prisma relations. User account deletion is not advertised or implemented as
  a complete self-service account-deletion flow in the inspected code.
- WhatsApp unsubscribe and user-level subscription removal are implemented.
- Users can unlink WhatsApp and remove saved social handles. Admins can disconnect
  connected social accounts. These operations remove app associations; provider
  OAuth/app consent cannot be revoked by the repository alone and requires the
  provider account controls.
- Users can revoke one or other active sessions.

Privacy/terms
- No public privacy policy or terms-of-service route/page was found.
- The public subscription records consent text/time/IP/source and supports STOP/
  unsubscribe, subject to live Meta webhook processing.
- Do not make a GDPR/CCPA/legal-compliance or "fully secure" claim without legal
  and implementation review.

H. LANDING PAGE CONTENT RECOMMENDATIONS

Suggested headline (strictly based on implemented capabilities)
- "Create, schedule and manage adverts across your connected channels"

Alternative verified-value headline
- "Choose an advert channel, reach your audience, and see every send's status"

Concise value proposition
- A role-aware dashboard that combines advert creation, AI/media policy review,
  channel schedules, WhatsApp audience subscriptions, campaign approvals and
  delivery status reporting.

Defensible benefits (3-6)
1. Create and preview adverts with platform-specific content and technical checks.
2. Schedule posts and channel runs through a Redis/BullMQ background worker.
3. Let users subscribe to adverts on their chosen platform.
4. Manage WhatsApp topic subscribers, consent, ownership confirmation, and opt-out.
5. Review audience sends before delivery when approval is required.
6. View recent posts, delivery outcomes, sessions and activity from one dashboard.

Strongest verified features to highlight
- Advert creation and platform policy review.
- Public `/subscribe` WhatsApp topic workflow.
- Channel schedule management.
- User per-platform subscriptions.
- Audience campaign approvals and status.
- Database-backed staff/user authorization and activity logs.

Simple how-it-works explanation
1. Staff create an advert and review platform checks.
2. Staff connect accounts and configure channels/schedules.
3. Users or WhatsApp-only subscribers choose matching adverts/topics.
4. The background worker sends, posts or proposes the delivery according to
   schedule and approval rules.
5. The dashboard reports platform-specific success or failure.

Platform names/logos safe to display
- The application has explicit integration code/UI for Facebook, Instagram,
  WhatsApp, X, and TikTok. Their names can be identified as intended integrations,
  but only after clearly qualifying that live connection/publishing is

  "connected" until credentials and live testing exist.

  options; both are currently credential-blocked in the inspected environment.

- Signed-out advert card: "Sign in to subscribe" -> /login with callback.
